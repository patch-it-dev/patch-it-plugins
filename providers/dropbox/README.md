# Dropbox

Every source patch-it reads for Dropbox, one section each: what it watches, why this source, what it reads and ignores, its known gaps. Each is registered in [`provider.go`](provider.go) and read by its kind ([`kinds/`](../../kinds/)); the saved copies its tests replay, and the golden files, are in [`testdata/`](testdata/README.md).

## Dropbox files API (`dropbox/files-api`)

### What it watches

Routes removed or added in the files namespace of Dropbox's own API spec (upload, download, copy, move, delete, search, properties, file requests): `files.stone` in [`dropbox/dropbox-api-spec`](https://github.com/dropbox/dropbox-api-spec), read at each commit that changed it.

Kind: `catalog` (`kinds/catalog`), the `Routes` reader (`kinds/catalog/routes.go`, new for this source).

### Why this source

- **Source:** [`files.stone`](https://github.com/dropbox/dropbox-api-spec/blob/main/files.stone) in dropbox/dropbox-api-spec, read raw at each commit (`https://raw.githubusercontent.com/dropbox/dropbox-api-spec/<sha>/files.stone`, a commit SHA never changing). Checked 2026-11-21: 67 routes, 69 commits to this file since 2016-05-24, 7 since 2026-01-01.
- **Why this one:** it's Dropbox's own IDL (Stone), the one file every official SDK (Python, JavaScript, .NET, Java, Swift, Objective-C) is generated from, and the repo's `README.md` says so directly. A route declared here and nowhere else is the ground truth for what a caller can call; the repo has no release tags, so a commit is the version, as for Convex's and Supabase's specs.
- **Alternatives considered:**
  - **`openapi/openapi.yaml`**, a full OpenAPI 3 document in the same repo, generated by Dropbox's own bot (`dropbox-spec-updater[bot]`) on every spec change. This is the more conventional, typed source (an `openapi` kind plugin, like `convex/deployment-api`), and it is genuinely official: checked 2026-11-21, it has 267 paths and 44 operations already marked `deprecated: true`, e.g. `POST /2/sharing/get_shared_links` ("DEPRECATED: Use list_shared_links instead. This endpoint will be retired in October 2026."). Not used for this source because the file is new (added 2026-11-17, two commits in its own history as of the date checked) and has no real removal in that short history yet to measure or replay; `files.stone` has nine years of commits and a real, dated one (see Quote). Worth revisiting once the OpenAPI export has more history of its own — its `deprecated` flags are a cleaner signal than Stone's free-text ` deprecated` suffix.
  - **The repo's commit messages**, which a bot (and, before it, `release_note_generator.py`) writes as structured "Added/Removed/Deprecated" bullets. Read by hand across the whole history for this page (see Quote and the next section); not used as the source itself because the bullets are prose, not every commit has them in the same shape (the `release_note_generator.py` era wrote `- Remove x, y routes`; the newer bot writes "### Removed files" or nothing for a removal that isn't a whole-file deletion), and the file itself is the more reliable thing to diff.
  - **`dropbox.com/developers`'s deprecations and changelog pages.** No page dedicated to API deprecations was found; Dropbox's own developer blog (`dropbox.tech`) covers deprecations in prose, years apart, with no feed. [See the community's own question](https://www.dropboxforum.com/discussions/101000014/is-there-any-open-api-a-k-a-swagger-spec-for-dropbox-api/786323) asking whether a machine-readable spec exists at all (it does: this one).
  - **The official SDKs' changelogs** (`dropbox-sdk-python`, `dropbox-sdk-js`): generated from this same spec; reading the spec directly is one source for every SDK instead of one per language.
- **Quote:** real commit `6c68656c` (2026-05-12) removes `route properties/remove(file_properties.RemovePropertiesArg, Void, file_properties.RemovePropertiesError) deprecated`, `properties/template/get` and `properties/template/list` (all three already marked `deprecated` in the commit before, `c8364404`, 2023-04-26) — the golden test's pair.

### How the provider announces changes

- **No API version.** Dropbox's REST API has no version number or date in its path (every route is under `/2/`); the event's `version` is the spec commit's committer date (UTC), the closest thing to the API version a change arrived in, as for Convex, Supabase and Appwrite.
- **A route is marked `deprecated` (optionally `deprecated by other_name`) in the file for a long time before it's ever removed**, often years: `change_file_member_access` was marked deprecated in 2017 (`4483042b`) and removed in 2021 (`4c2256e5`); `properties/remove` and its two siblings were deprecated well before 2023 and removed in 2026. This source doesn't read the `deprecated` marker itself (see below): it reports the removal, which is the point a caller's existing code actually breaks.
- **The file is edited in bursts**, not steadily: no commit touched `files.stone` between 2023-04-26 and 2026-05-12, then seven times from May to November 2026.

### What the plugin reads and ignores

- **Reads** every line matching `^route name(...)`, by name only (never the route's argument, result or error types, or whether it's marked `deprecated`): a name in the older commit's file and gone from the newer's is a `breaking` `api_operation` event; a name new in the newer commit's file is `added`. The excerpt quotes the whole declaration line, deprecation marker included when there is one.
- **Ignores** everything else in the file: structs, unions, docstrings, route attributes (`attrs`, `scope`, `is_preview`…) and whether a surviving route's own signature changed shape. A route that keeps its name but changes its request or response type isn't seen.
- **A route renamed to a different Stone spelling for the same real call is matched by operation, not name, and isn't an event.** Real and found by walking the full history, not from the saved fixtures: on 2018-08-14 (`ff540e4a`) Dropbox renamed `copy_v2`, `create_folder_v2`, `delete_v2`, `move_v2` and `upload_session/append_v2` to `copy:2`, `create_folder:2`, `delete:2`, `move:2` and `upload_session/append:2` — every one still the same `/2/files/<x>_v2` call. A route moving to or from another namespace (`files.stone` is the only file this source reads) would still read as one removal and one addition, since the rename match only looks within one commit's pair.
- **A reorder or reformat of the file is never a change.** The file's July-to-November 2026 commits reorder large stretches of `files.stone` (confirmed on the 2026-05-12 commit: a line diff of that single commit shows nearly every route as both removed and re-added); comparing the set of declared names, not lines, is why that reads as no change. The golden test is pinned on exactly that commit for this reason.
- **The pinned drop test:** the next real commit (`a4fc0169`, 2026-06-07) only edits comments and `@common.Deprecated` field annotations inside structs — zero route names appear or disappear, and zero events are stored.

### Known gaps

- **Deprecation isn't its own event yet.** A route marked `deprecated` in the file, with its replacement still working, isn't reported until the route is actually removed — unlike `eol`'s or `changelog/json`'s sources, which emit a `deprecated` event at the announcement. Dropbox's deprecations run for years (see above), so this misses real advance notice; reading the ` deprecated` / ` deprecated by x` suffix is a natural next step, probably alongside switching to `openapi/openapi.yaml` once it has history (see Alternatives considered).
- **Only the files namespace is read.** Dropbox's spec has about twenty other namespaces (`sharing`, `team`, `paper`, `account`…); each would be its own source, same reader, a different `Path`.
- **The patch-it client needs `dropbox` in its list of date-versioned APIs** to place these events' date `version`, as `convex`, `supabase` and `appwrite` do; that list is outside this repo.
- **A route whose name is reused for something unrelated reads as unchanged.** Stone has no stable identifier beyond the name; this hasn't happened in this file's history.

## Python SDK (`dropbox/python-surface`)

### What it watches

The public API of the `dropbox` package on PyPI, release by release: classes, functions and methods removed or renamed, parameters removed, and parameters that lost their default (callers must now pass them). One `package_release` event per change. Every final release is listed from PyPI, and each consecutive pair is compared. What a release adds is an `added` event.

Kind: `apisurface` (`kinds/apisurface`), with the Python reader (`kinds/apisurface/pysurface`).

### Why this source

- **Source:** the release files on PyPI (<https://pypi.org/project/dropbox/>), each release's wheel read as published; the code is at <https://github.com/dropbox/dropbox-sdk-python>. Checked 2026-11-22.
- **Why this one, next to `files-api`:** nearly all of the package is generated by Stone from the same spec (`base.py`, `files.py`, `sharing.py`, `team.py`…), so this isn't a second view of hand-written code: it's the spec as Python callers see it. That covers what `files-api` doesn't read: every namespace, not only `files`, and every method's parameters, not only route names. Walked against the real wheels of every final release from 11.0.0 to 12.2.5 on 2026-11-22: 46 breaking events over 49 pairs, every one in a generated module, e.g. `files_get_thumbnail`'s `quality` parameter gone in 12.2.2 (a call passing it raises `TypeError`; `files-api` can't see a parameter) and `team.BulkSuspend*` gone in 12.2.3 (the `team` namespace). Where a route in the `files` namespace is removed, both sources report it, once as a route and once as a method (`files_properties_remove`, 12.2.0, is `properties/remove` in `files-api`'s golden test); OpenAI's `openai/api` and `openai/python-surface` overlap the same way.
- **Alternatives considered:** `UPGRADING.md` in the same repo (major versions only, prose); GitHub release notes (lists of "Automated Spec Update" pull requests, no per-method detail).
- **Quote:** `def sharing_remove_file_member(self, file, member)` (`dropbox/base.py` line 6054, already warning `"remove_file_member is deprecated."`) at 12.2.3, gone at 12.2.4.

### How the provider announces changes

- **A patch release can break.** 12.2.2, 12.2.3, 12.2.4 and 12.2.5 each removed public methods, parameters or classes: the SDK is regenerated whenever the spec changes, and a route the spec drops leaves the SDK in the next release, deprecated or not.
- **Releases are yanked:** 10.11.0 and 12.0.0 are, and aren't listed: a pair skips them.
- **Forced on upgrade**, for a repo whose pin reaches the release.

### What the plugin reads and ignores

- Reads the `.py` files under `dropbox/` in the release's wheel as text, never importing or running them, by the kind's rules (see `redis/redis-py-surface`): module-level classes and functions, the methods of module-level classes, their parameters and defaults, `__all__`, and `__init__.py`'s re-exports.
- Ignores private names, including a name left out of its module's `__all__`.
- A generated method is named for its class: `base.DropboxBase.sharing_remove_file_member`, the method customer code calls on `dropbox.Dropbox`, which inherits it.
- The pinned drop test: 12.2.0 → 12.2.1 reformats most of `base.py`'s method signatures (169 of its 180 methods split one parameter per line at 12.2.0, 34 at 12.2.1) and changes none: no events.

### Known gaps

- The kind's own gaps (see `redis/redis-py-surface`): a positional parameter renamed reads as removed; type changes aren't events.
- **A module named like its package reads ambiguously.** In 10.10.0 → 11.0.0 (the real pair; 10.11.0 is yanked), `dropbox/dropbox.py` became `dropbox/dropbox_client.py`, and the event for its `Dropbox` class reads `dropbox.Dropbox` removed, though `dropbox.Dropbox` from the package (what nearly every caller writes) kept working; only `dropbox.dropbox.Dropbox` broke. No module by that name has existed since, so this can't recur, but a backfill over that pair emits it.
- **`dropbox-sdk-js`** (npm `dropbox`), generated the same way, isn't read yet: same kind, a second source.
